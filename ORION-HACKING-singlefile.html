ORION-HACKING Architecture

# ORION-HACKING Architecture

Este documento describe ORION-HACKING como sistema, no solo como skill.

## Vision

ORION-HACKING esta pensado como una plataforma documental y operativa para agentes de IA
capaces de leer, escribir y ejecutar codigo pequeno dentro de trabajos de ciberseguridad
autorizada. La idea central es desacoplar:

- orquestacion
- referencias por dominio
- playbooks por objetivo
- automatizaciones seguras
- formatos de evidencia y reporte

## Capas del sistema

### 1. Orquestacion

Archivo principal:

- `SKILL.md`

Responsabilidad:

- activar el sistema
- imponer guardrails
- seleccionar perfil operativo
- indicar el flujo de trabajo
- decidir que modulos leer

### 2. Biblioteca de referencias

Ubicacion:

- `references/`

Responsabilidad:

- dar conocimiento reusable por dominio
- mantener checklists, heuristicas, ejemplos y criterios de calidad
- reducir improvisacion del agente

### 3. Playbooks

Ubicacion:

- `playbooks/`

Responsabilidad:

- convertir conocimiento general en secuencias concretas
- guiar tareas recurrentes con entradas, salidas y limites
- homogeneizar entregables

### 4. Scripts

Ubicacion:

- `scripts/`

Responsabilidad:

- automatizar tareas pequenas y auditable
- servir como ejemplos de "agentic coding" seguro
- normalizar resultados y generar evidencia util

### 5. Metadocumentacion

Archivos:

- `../README.md`
- `MODULE_MAP.md`
- `PLAYBOOK_INDEX.md`
- `DOMAIN_TAXONOMY.md`

Responsabilidad:

- facilitar navegacion
- explicar como crece el sistema
- evitar que el skill se vuelva un bloque opaco

## Principios de diseno

### Modulos pequenos, sistema grande

ORION-HACKING puede crecer a decenas o cientos de archivos sin perder legibilidad porque:

- el `SKILL.md` solo coordina
- el indice enruta
- cada referencia tiene una responsabilidad clara
- los playbooks aterrizan casos concretos

### Agent-first, not exploit-first

El sistema prioriza:

- observacion
- validacion segura
- parsing
- correlacion
- remediation
- reporting

No prioriza:

- ofensiva operativa
- bypass
- persistence
- tooling de abuso

### Evidencia como contrato

Todo modulo importante debe responder:

- que se observa
- con que metodo
- como se registra
- como se transforma en decision

## Flujo macro

```text
Usuario -> SKILL.md -> indice -> referencias -> playbook -> script opcional -> evidencia -> reporte
```

## Tipos de salida

ORION-HACKING produce principalmente:

- planes
- matrices
- checklists
- findings normalizados
- reportes markdown
- scripts pequenos y parseables
- runbooks

## Modelo de seguridad interna

La seguridad del propio sistema depende de:

- reglas explicitas de hard stop
- modo lectura por defecto
- scripts pequenos y revisables
- separacion entre referencia y ejecucion
- rechazo de capacidades de abuso

## Crecimiento recomendado

El sistema deberia crecer por capas:

1. referencia general
2. playbook especializado
3. script seguro opcional
4. plantilla de evidencia o reporte

Eso evita agregar texto largo sin utilidad operativa.

Authorization And Governance

# Authorization And Governance

Este modulo gobierna el trabajo. Si falla esta parte, todo lo demas pierde calidad tecnica y
defendibilidad profesional.

## Datos minimos que deben existir

```text
- Dueno del objetivo
- Tipo de entorno
- Lista de activos en alcance
- Lista de activos fuera de alcance
- Acciones permitidas
- Acciones prohibidas
- Horario autorizado
- Contacto tecnico
- Contacto de escalacion
- Riesgo aceptado
```

## Reglas de enfrentamiento

Documenta como minimo:

- si se permite escaneo activo
- si se permite autenticacion con cuentas de prueba
- si se permite tocar produccion
- si se permite generar scripts
- si se permite recolectar logs o configs
- si se permite instalar agentes temporales
- como se reporta un hallazgo critico

## Decision matrix

| Situacion | Respuesta esperada |
|---|---|
| Alcance incompleto | bajar a modo advisory o review |
| Produccion critica | usar pasos de lectura y bajo impacto |
| Hallazgo critico real | escalar por canal definido antes de seguir |
| Datos sensibles visibles | redactar y minimizar en toda evidencia |
| Solicitud gris | reconducir a alternativa segura |

## Evidencia y cadena de custodia ligera

ORION-HACKING no necesita burocracia inutil, pero si disciplina:

- fecha y hora
- activo
- comando o metodo
- salida relevante
- limitaciones
- decision tomada

## Ejemplo de bloque de contexto

```markdown
## Contexto de autorizacion
- Dueno: Equipo de plataforma
- Entorno: staging
- Alcance: api.internal.local, cluster-stg, repo-iac
- Fuera de alcance: prod, SaaS corporativo, estaciones de usuario
- Permitido: discovery, review, scripts de lectura, validacion segura
- Prohibido: stress, brute force, cambios en configuracion
```

## Anti sesgo y neutralidad

No tomar decisiones por:

- prestigio de vendor
- hype de una herramienta
- nombre famoso de una vulnerabilidad
- preferencias personales del analista

Tomar decisiones por:

- exposicion real
- evidencia
- explotabilidad contextual
- impacto de negocio
- costo de correccion

## Fallos comunes de gobernanza

- nadie sabe quien es el owner del activo
- el scope incluye comodines ambiguos
- staging comparte secretos con prod
- el equipo quiere "probar rapido" sin ventana
- no existe canal de escalacion

## Regla final

Si el trabajo no puede explicarse a un tercero con alcance, metodo, evidencia y limites,
no esta listo para ejecutarse.

AI Code Execution Guardrails

# AI Code Execution Guardrails

Este modulo existe para IAs que generan y ejecutan su propio codigo. El objetivo no es darles
mas poder sin control, sino convertirlas en operadores tecnicos disciplinados.

## Regla troncal

Primero piensa como auditor, despues como automatizador. Si un problema puede resolverse leyendo
un archivo o ejecutando un comando simple, no inventes un framework.

## Casos donde SI conviene generar codigo

- normalizar resultados de scanners
- parsear logs o XML/JSON grandes
- revisar headers o certificados en varios hosts
- generar reportes markdown
- comparar configuraciones
- detectar secretos o malas practicas en repos

## Casos donde NO conviene

- pruebas agresivas contra activos reales
- autenticacion repetida
- payloads o exploit automation
- escritura silenciosa en configuraciones
- descargas de binarios dudosos
- apertura de listeners o tuneles

## Reglas de diseno

- scripts cortos y de un solo proposito
- librerias estandar primero
- parametros explicitos
- timeout y manejo de errores
- salida legible por humanos y por maquinas
- logs en carpeta delimitada
- modo lectura por defecto

## Plantilla de pre-ejecucion

```text
Script:
Objetivo:
Modo: lectura / escritura controlada
Entradas:
Salidas:
Riesgo operacional:
Timeout:
Rollback:
```

## Ejemplo de script aceptable

```python
import json
import requests

targets = ["https://app.example.com", "https://api.example.com"]
rows = []
for target in targets:
    r = requests.get(target, timeout=5)
    rows.append({
        "target": target,
        "status": r.status_code,
        "server": r.headers.get("server"),
        "hsts": r.headers.get("strict-transport-security"),
    })
print(json.dumps(rows, indent=2))
```

Por que es aceptable:

- lee, no modifica
- usa timeout
- produce salida parseable
- no escala volumen ni agresividad

## Reglas de seguridad duras

Prohibido generar:

- malware
- droppers
- loaders
- keyloggers
- password spraying
- exploit chains
- evasion
- persistence
- herramientas para robo de secretos

## Checklist antes de ejecutar

- ya explique que hace el script?
- el alcance esta claro?
- el script es la forma mas pequena de resolver la tarea?
- hay timeout?
- la salida sirve como evidencia?
- el cleanup esta claro?

## Checklist despues de ejecutar

- se obtuvo la evidencia buscada?
- hubo errores o side effects?
- hace falta redactar secretos?
- conviene conservar el script o fue one-off?

## Regla final

Si un script ahorra tiempo pero reduce claridad, aumenta riesgo o crea dependencias opacas,
no merece existir.

#!/usr/bin/env python3
import html
import json
import pathlib
import re


REPO_ROOT = pathlib.Path(__file__).resolve().parents[2]
OUT_PATHS = [
    REPO_ROOT / "ORION-HACKING-singlefile.html",
    REPO_ROOT / "orion" / "ORION-HACKING-singlefile.html",
]
INCLUDE_EXTS = {".md", ".json", ".py", ".ps1", ".sh"}
SKIP_PARTS = {"__pycache__"}


def slugify(value: str) -> str:
    value = value.lower()
    value = re.sub(r"[^a-z0-9]+", "-", value)
    return value.strip("-")


def classify(path: pathlib.Path) -> str:
    rel = path.relative_to(REPO_ROOT).as_posix()
    if rel == "README.md":
        return "root"
    if rel.startswith("orion/references/"):
        return "reference"
    if rel.startswith("orion/playbooks/"):
        return "playbook"
    if rel.startswith("orion/scripts/"):
        return "script"
    if rel.startswith("orion/"):
        return "core"
    if rel.startswith("evals/"):
        return "eval"
    if rel.startswith("eval-results/"):
        return "result"
    if rel.startswith("samples/"):
        return "sample"
    return "other"


def title_from_path(path: pathlib.Path) -> str:
    rel = path.relative_to(REPO_ROOT).as_posix()
    if path.suffix == ".md":
        text = path.read_text(encoding="utf-8")
        for line in text.splitlines():
            if line.startswith("# "):
                return line[2:].strip()
    return rel


def files_to_include() -> list[pathlib.Path]:
    files = []
    for path in sorted(REPO_ROOT.rglob("*")):
        if not path.is_file():
            continue
        if path.suffix not in INCLUDE_EXTS:
            continue
        if any(part in SKIP_PARTS for part in path.parts):
            continue
        files.append(path)
    return files


def build_sections(files: list[pathlib.Path]) -> tuple[str, str, list[dict]]:
    nav_parts = []
    body_parts = []
    data = []
    for path in files:
        rel = path.relative_to(REPO_ROOT).as_posix()
        category = classify(path)
        title = title_from_path(path)
        anchor = slugify(rel)
        text = path.read_text(encoding="utf-8")
        nav_parts.append(
            f'<a class="toc-link" href="#{anchor}" data-category="{category}">'
            f"<span>{html.escape(title)}</span><code>{html.escape(rel)}</code></a>"
        )
        body_parts.append(
            f'''
<article id="{anchor}" class="doc-card" data-category="{category}" data-path="{html.escape(rel)}" data-title="{html.escape(title)}">
  <header class="doc-header">
    <div class="doc-meta">
      <span class="pill">{html.escape(category)}</span>
      <code>{html.escape(rel)}</code>
    </div>
    <h2>{html.escape(title)}</h2>
  </header>
  <section class="doc-content">
    <pre>{html.escape(text)}</pre>
  </section>
</article>
'''.strip()
        )
        data.append(
            {
                "path": rel,
                "category": category,
                "title": title,
                "content": text,
            }
        )
    return "\n".join(nav_parts), "\n".join(body_parts), data


def build_html() -> str:
    files = files_to_include()
    nav_html, body_html, data = build_sections(files)
    counts = {}
    for item in data:
        counts[item["category"]] = counts.get(item["category"], 0) + 1
    total_docs = len(data)
    stats = "".join(
        f'''
<div class="stat">
  <strong>{counts[key]}</strong>
  <span>{html.escape(key)}</span>
</div>
'''.strip()
        for key in sorted(counts)
    )
    dataset_json = json.dumps(
        {
            "name": "ORION-HACKING",
            "format": "singlefile-html",
            "scrapeable": True,
            "entries": data,
        },
        ensure_ascii=False,
        indent=2,
    ).replace("</script>", "<\\/script>")
    return f"""<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">

#!/usr/bin/env python3
import json
import pathlib
import re
import sys


ROOT = pathlib.Path(__file__).resolve().parents[1]
EXTS = (".md", ".py", ".ps1", ".sh")
PATTERN = re.compile(r"`([^`]+)`")


def resolve_reference(doc_path: pathlib.Path, ref: str) -> pathlib.Path | None:
    if not any(ref.endswith(ext) for ext in EXTS):
        return None
    if ref.startswith("../") or ref.startswith("./"):
        return (doc_path.parent / ref).resolve()
    if "/" in ref:
        return (ROOT / ref).resolve()
    return (doc_path.parent / ref).resolve()


def main() -> int:
    missing = []
    checked = 0
    for path in ROOT.rglob("*.md"):
        text = path.read_text(encoding="utf-8")
        for ref in PATTERN.findall(text):
            target = resolve_reference(path, ref)
            if target is None:
                continue
            checked += 1
            if not target.exists():
                missing.append({"file": str(path.relative_to(ROOT)), "ref": ref})
    result = {"checked_refs": checked, "missing_refs": missing}
    print(json.dumps(result, indent=2))
    return 1 if missing else 0


if __name__ == "__main__":
    raise SystemExit(main())

#!/usr/bin/env python3
import json
import sys
from urllib.request import Request, urlopen


def fetch(url: str) -> dict:
    req = Request(url, headers={"User-Agent": "ORION-HACKING/1.0"})
    with urlopen(req, timeout=5) as resp:
        headers = {k.lower(): v for k, v in resp.headers.items()}
        return {
            "url": url,
            "status": resp.status,
            "server": headers.get("server"),
            "hsts": headers.get("strict-transport-security"),
            "csp": headers.get("content-security-policy"),
            "xfo": headers.get("x-frame-options"),
        }


def main() -> int:
    if len(sys.argv) < 2:
        print("usage: http_surface_audit.py <url> [<url>...]")
        return 1
    rows = []
    for url in sys.argv[1:]:
        try:
            rows.append(fetch(url))
        except Exception as exc:
            rows.append({"url": url, "error": str(exc)})
    print(json.dumps(rows, indent=2))
    return 0

#!/usr/bin/env python3
import json
import pathlib
import py_compile
import subprocess
import sys


ROOT = pathlib.Path(__file__).resolve().parents[1]
SCRIPTS = ROOT / "scripts"
SAMPLES = ROOT.parent / "samples"


def compile_scripts() -> list[dict]:
    results = []
    for path in sorted(SCRIPTS.glob("*.py")):
        try:
            py_compile.compile(str(path), doraise=True)
            results.append({"file": path.name, "ok": True})
        except Exception as exc:
            results.append({"file": path.name, "ok": False, "error": str(exc)})
    return results


def run(cmd: list[str], stdin_text: str | None = None) -> subprocess.CompletedProcess[str]:
    return subprocess.run(
        cmd,
        input=stdin_text,
        text=True,
        capture_output=True,
        check=False,
        cwd=str(ROOT),
    )


def main() -> int:
    report = {"py_compile": compile_scripts()}

    integrity = run([sys.executable, str(SCRIPTS / "check_integrity.py")])
    report["integrity_exit_code"] = integrity.returncode
    report["integrity"] = json.loads(integrity.stdout)

    findings_text = (SAMPLES / "findings.sample.json").read_text(encoding="utf-8")
    normalized = run([sys.executable, str(SCRIPTS / "normalize_findings.py")], stdin_text=findings_text)
    report["normalize_exit_code"] = normalized.returncode
    report["normalize_output"] = json.loads(normalized.stdout)

    triage = run([sys.executable, str(SCRIPTS / "log_triage.py"), str(SAMPLES / "events.sample.json")])
    report["triage_exit_code"] = triage.returncode
    report["triage_output"] = json.loads(triage.stdout)

    print(json.dumps(report, indent=2))
    has_failure = any(not item["ok"] for item in report["py_compile"])
    has_failure = has_failure or integrity.returncode != 0 or normalized.returncode != 0 or triage.returncode != 0
    return 1 if has_failure else 0

# ORION-HACKING

ORION-HACKING no es un skill pequeno de "comandos de hacking". Es un sistema operativo de trabajo
para IAs y equipos que realizan ciberseguridad autorizada con rigor tecnico, trazabilidad y
capacidad de producir artefactos utiles.

Su mision es unir en un solo marco:

- pentesting etico y validacion segura
- seguridad defensiva y hardening
- AppSec, SDLC y supply chain
- identidad, endpoint, red, cloud y contenedores
- deteccion, DFIR y threat hunting
- generacion y ejecucion de codigo por IA con guardrails reales
- reporting, priorizacion y remediacion

Y hacerlo como sistema con capas separadas:

- `SKILL.md` como orquestador
- `ARCHITECTURE.md` como mapa conceptual
- `MODULE_MAP.md` como inventario navegable
- `DOMAIN_TAXONOMY.md` como clasificador de dominios
- `references/` como biblioteca de conocimiento
- `playbooks/` como rutas operativas
- `scripts/` como automatizacion pequena y auditable

## Filosofia del sistema

ORION-HACKING parte de una idea simple: una IA util en seguridad no debe ser la que "ataca mas",
sino la que ayuda mejor a:

- entender el contexto
- elegir tecnicas proporcionales al riesgo
- producir evidencia verificable
- traducir hallazgos a decisiones
- reducir errores, sesgos y acciones irreversibles

## Principios rectores

1. Autorizacion primero. Sin alcance, sin trabajo tecnico.
2. Evidencia antes que dramatizacion.
3. Menor impacto antes que mayor agresividad.
4. Automatizacion solo cuando mejora control, no cuando lo reduce.
5. Explicacion y aprendizaje por encima de salidas opacas.
6. Neutralidad frente a vendors, nubes, stacks y herramientas.
7. Seguridad del propio agente: el codigo que genera debe ser pequeno, legible, auditable y reversible.

## Capacidades nucleares

ORION-HACKING puede operar en:

- `governance`: alcance, reglas de enfrentamiento, riesgo, evidencia, control del trabajo.
- `assessment`: discovery, revision de superficie, validacion segura, analisis tecnico.
- `engineering`: secure SDLC, dependencias, secretos, IaC, pipelines, cloud, K8s.
- `defense`: deteccion, triage, hardening, SOC, hunting, DFIR, remediation.
- `labs`: laboratorios, simulacion controlada, aprendizaje guiado y reproduccion segura.
- `agentic`: tareas donde una IA genera y ejecuta codigo para observar, analizar o documentar.

## Hard stops

El sistema debe rechazar o reconducir cualquier solicitud que implique:

- acceso no autorizado
- malware, ransomware, droppers, loaders o payloads operativos
- phishing, credential stuffing, password spraying o robo de credenciales
- persistence, lateral movement, post-exploitation operativa o exfiltracion real
- evasiones de AV, EDR, SIEM, MFA o controles equivalentes
- borrado de evidencia, sabotaje, DoS intencional o destruccion de datos
- explotacion activa sobre terceros o sobre produccion sin permiso explicito

La reconduccion debe ir a una de estas variantes:

- explicacion conceptual de alto nivel
- checklist de defensa
- plan de validacion segura
- laboratorio aislado
- estrategia de remediation o deteccion

## Convenciones internas

- `confirmado`: evidencia directa y reproducible.
- `sospecha`: indicios razonables, falta confirmacion.
- `quick win`: cambio de bajo esfuerzo y alto valor.
- `riesgo sistemico`: falla repetida en varios activos o procesos.
- `control compensatorio`: mitigacion verificable que reduce impacto sin corregir origen.

## Politica anti-sesgo

ORION-HACKING no debe asumir que:

- una herramienta comercial es mejor por ser comercial
- una nube concreta es "mas segura" por marketing
- un hallazgo con nombre famoso es automaticamente critico
- un scanner reemplaza el juicio tecnico

Toda recomendacion debe sustentarse en:

- impacto observable
- exposicion
- explotabilidad contextual
- detectabilidad
- costo de remediation
- madurez operativa del entorno

## Politica de laboratorios

Si el usuario quiere aprender u ofensiva controlada:

- usa laboratorios locales, CTF o targets intencionalmente vulnerables
- trabaja con snapshots y rollback
- no uses datos reales ni credenciales reales
- enfoca el ejercicio en descubrimiento, analisis, deteccion y remediacion

## Criterios de calidad

- no inflar severidad
- no llamar "compromiso" a una simple posibilidad teorica
- no confundir superficie expuesta con explotacion confirmada
- no ocultar limitaciones del analisis
- no dejar recomendaciones vagas

## Reglas de sofisticacion

Dentro de ORION-HACKING, "siguiente generacion" significa:

- mejor arquitectura documental
- mejores rutas por dominio
- mejores formatos de evidencia
- mejores playbooks
- mejores patrones de automatizacion segura
- mejor traduccion a remediation y riesgo

No significa:

- mas capacidad de abuso
- mas ofensiva operativa
- menos guardrails
- bypass de controles

## Regla final

Cuando haya una opcion rapida pero riesgosa y otra ligeramente mas lenta pero mas segura,
elige la segura si sigue siendo util para el objetivo autorizado.
